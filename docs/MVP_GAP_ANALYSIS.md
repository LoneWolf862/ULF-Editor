### Reproduced and inspected findings

1. **Inventory Apply can change the prefab during a quality-only edit.** Selecting synthetic Wood displayed `Wood` while the editable combo retained `ArrowFire` as its selected data. `apply_slot()` preferred that data and replaced the hash. The same offscreen check replaced a synthetic unknown hash. Filtering and typed entries share this ambiguous selection path. `refresh()` also clears the internal selection even when Apply reselects a visible cell, so a subsequent Apply can silently do nothing until another click.
2. **Stack limits are unenforced.** The UI and writer use a generic 1–65,535 range. The catalog's `max_stack` fields are unused for validation, and the file provides no source or version to establish their authority. Treat all starter values as unverified until checked.
3. **Skill editing can partially apply and silently lose precision.** In an offscreen check, the first row changed to 44 even though the next row was invalid. The export handler calls the same routine and continues after it reports an error. Source inspection shows that export also re-applies all displayed values rounded to three decimals, and inventory refresh rebuilds the skills table, discarding pending text edits.
4. **Export verifies bytes before writing.** The desktop reparses the in-memory output, checks two metadata fields, and writes directly to the chosen path. It lacks post-write read-back, atomic publication, failure cleanup, and semantic verification. A resolved path comparison covers ordinary aliases, while distinct hard links can still refer to the same source file.

## Technical risks and decisions

- **Format assumptions can survive a no-op round trip.** The two samples exercise only 46/33/109/2. A parser can preserve or reconstruct bytes while still misidentifying semantics. Treat other advertised combinations as unverified and use independent format evidence before extending the allowlist.
- **Catalog data determines whether inventory edits are safe.** A wrong prefab mapping or game-version limit can produce a structurally valid but incorrect save. Require reviewed version-specific sources and collision checks. Preserve unknown records exactly unless an explicit quantity edit has a verified maximum.
- **UI state can corrupt intent before serialization.** Stale combo data, rounded skill display, and refresh-driven state loss cross otherwise valid parser/writer boundaries. Keep displayed values separate from original bytes and use explicit staged commands.
- **Filesystem semantics vary.** Enforce Save As and reject aliases of the source. Test existing targets, locked files, permissions, and publication failure on supported platforms.
- **Coverage currently overstates confidence if skips are overlooked.** One passing hash type check does not establish save compatibility. Synthetic fixtures must cover meaningful failures and data preservation. Keep real saves and private identifiers out of fixtures, reports beyond redacted diagnostics, and release artifacts.
