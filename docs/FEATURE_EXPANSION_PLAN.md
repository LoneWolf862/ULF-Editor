# ULF Editor feature expansion plan

## Current milestone update — 2026-11-13

The owner subsequently approved and released Alpha 0.3.1, then explicitly
scheduled **Alpha 0.4 Advanced Inventory Management**. That assignment supersedes
the proposed milestone naming/sequencing below, not the approved requirements.
The historical assessment below is retained as research and is not a current
implementation inventory.

Alpha 0.4 now implements session Undo/Redo, transactional move/swap, drag/drop,
previewed duplicate/replacement/fill and a conservative verified equipment-slot
workflow. Windows automated validation passes 126 tests; native Linux and
Alpha 0.4 game acceptance remain pending. See the
[implementation, policy proposals and owner checklist](ALPHA_0.4_INVENTORY_MANAGEMENT.md).
Automatic sorting, broader custom/variant copy policies, context-dependent
equipment and recovery remain deferred. REQUIREMENTS.md is unchanged; proposals
remain proposals until explicitly approved. The next gate is owner acceptance,
not another feature implementation or release merge.

## 2. Recommended milestones and gates

The proposed Alpha 0.3 equipment/organization bundle conflicts with the approved baseline. Section 2 assigns 0.3 to desktop polish and section 4.8 and D-11 place equipment and advanced organization after MVP. Keep the baseline sequencing pending an explicit owner decision.

| Order | Proposed slice | Gate and dependencies |
|---|---|---|
| 0 | Finish Alpha 0.2 acceptance and prioritize current-build format compatibility | Keep the existing allowlist and add a separately approved 47/34/110/2 compatibility effort. Pin actual writer/reader methods, create synthetic format fixtures, run a disposable-save and native offline matrix, verify catalog inventory eligibility and review distribution evidence. Deliver supported-build diagnostics even when an unsupported save cannot be opened. |
| 1 | Alpha 0.3 desktop polish | Deliver baseline review, undo/redo, keyboard/accessibility improvements and separate-file recovery. Propose read-only verified item statistics and single-item repair as small additions after the catalog and quantization gates. Approve them separately if they affect release scope. |
| 2 | Post-MVP inventory and equipment | Start with Fill Stack, then previewed Repair/Fill All and atomic replacement. Add move/swap, then constrained duplication, eligible clear, and equipment validation. Defer drag-and-drop until the same keyboard-safe commands work. Schedule as its own milestone unless the owner approves a revised Alpha 0.3 scope. |
| 3 | Proposed Alpha 0.4 character customization | Deliver read-only section diagnostics first. Add appearance and name independently, then power/cooldown. Verify food reconstruction and runtime vitals before enabling those writes. The name feature needs a Forge-state disclosure. |
| 4 | Proposed Alpha 0.5 knowledge and skill management | Begin with read-only knowledge and additive changes to verified identifiers. Build presets and bulk skill operations on the existing skill batch path and shared undo. Defer removals and cross-record cascades until in-game prerequisites and rediscovery behavior are verified. |
| 5 | Proposed Alpha 0.6 advanced items and mod compatibility | Add data-only overlays with field-level verification. Then enable eligible quantity-only edits, supported variants, crafter display/edit and namespaced typed metadata in separate slices. Keep unsupported and executable metadata opaque. |

The milestone names after Alpha 0.3 are proposals. A version number never substitutes for its compatibility and preservation gates.

## 3. Item and equipment operation specification

| Operation | Proposed behavior and safety |
|---|---|
| Stats preview | Label **Stored** fields separately from **Calculated** properties. Show old → proposed derived values when quality changes. Use one identified build snapshot. Report unknown or inapplicable values explicitly. Distinguish ordinary max quality from format max and gameplay verification. See [item-stat research](ITEM_STAT_SCALING.md). |
| Durability and repair | Show stored current, verified maximum, and percentage. Preserve current on quality-only edits even if the new maximum is lower. Flag over-maximum values and offer an explicit correction. Repair writes only durability to the build-matched, representable maximum for an eligible damaged item. Repair All previews each proposed edit and excluded record with its reason, then commits once. Skip already full, unsupported or above-max items by default. Disable computed repair when applicability, coefficients or safe encoding are unavailable. |
| Fill one or all | Use the same verified cap and domain bounds as manual quantity. Fill All lists old/new counts, skips protected or already full items and requires confirmation. Preserved oversized stacks are displayed and left alone until explicitly corrected. |
| Duplicate | Start with verified vanilla items using ordinary new-item rules. Preserve only explicitly approved transferable fields, with a visible preview, valid slot, verified limit and new-item flags unset. Keep source flags and original data unchanged. Disable duplication for cheated, ambiguous or opaque/custom-bearing records until there is an approved semantics contract. Unknown metadata is never silently copied into an invented record or discarded from the original. |
| Replace | Stage removal of a selected eligible record and add a separately validated prefab in its slot in a single transaction. Show both records, use explicit new-item defaults, require confirmation, and preserve the old record if any part fails. |
| Move and swap | Move a whole retained record to a verified writable free slot. Swap two selected identities as one proposal and preserve non-position bytes. Reject duplicate coordinates, unresolved capacity, ambiguous records and unknown items whose byte-preservation rules forbid movement. Avoid implicit displacement. |
| Clear inventory | Preview counts, identities and exclusions. Block a literal “Clear Inventory” when protected records prevent a true clear. Offer “Remove eligible items” with explicit confirmation and exact exclusions. Maintain current unknown-record removal protections. |
| Equip and unequip | Derive a read-only slot/hand view first. `Player.EquipInventoryItems` runs each saved equipped record through `Humanoid.EquipItem` and clears flags on records it cannot equip. Verify one-per-slot and main/off-hand/two-handed constraints from build rules and assets. Handle ammo, hidden slots, utility and trinkets explicitly when verified. Preview any displacement and validate the entire resulting loadout. |
| Crafter, variants and custom data | Treat crafter ID and name as one versioned optional field. Start with read-only display and a clearly labeled display-name edit with explicit identity preservation, subject to owner approval and flag/encoding evidence. Require a verified integer variant set per prefab. Edit only approved, namespaced custom keys with schema and size bounds. Preserve unknown key order, duplicates, raw string encoding and unrelated bytes. Block when duplicate keys make the intended edit ambiguous. |
| Undo/redo | Record immutable accepted proposals by stable identity and scoped before/after data. Undo/replay through the same validators, restore exact prior bytes, and treat bulk actions as one entry. New apply after undo clears redo. Opening another save starts a new history. Save As records an exported revision. Undo cannot rewrite a file already exported. |

## 4. Character customization evidence and validation

The table records current writer/reader behavior verified by local CIL inspection of build 26249040. Offset and representation evidence applies to the stated method and build. The byte spans must be proved separately on supported layouts before enabling writes. The current codec's head, middle and tail handling is an implementation boundary, and a successful opaque round-trip does not identify fields. [Build provenance and method inspection](ITEM_STAT_SCALING.md).

| Capability | Local serialization evidence and load behavior | Proposed edit guard |
|---|---|---|
| Character display name | `PlayerProfile.SavePlayerToDisk` writes the profile name string, followed by the player ID and start seed. The game UI separately derives a file key at character creation. `Player.GetItemUpgradeChance` reads the player name when initializing missing Forge seed entries. | Use the version-specific game name validator and a measured length limit before exposing edits. Reject control characters, NUL and disallowed characters. Keep file key, player ID, seed, existing upgrade seed table and all unrelated bytes. Explain the possible change to future Forge initialization and preserve past records. [Iron Gate's 1.0.21 name validation note](https://www.valheim.com/news/patch-1-0-21/). |
| Body/model | `Player.Save` writes a model index as int32 after the color vectors. `Player.Load` invokes `SetPlayerModel`, which passes the index to visual equipment. | Permit only indices enumerated and verified from the matching player prefab. Keep unknown existing indices opaque. Never infer from the integer range. |
| Hair and beard | `Player.Save` writes beard then hair string before color vectors. `Player.Load` calls corresponding Humanoid setters. | Verified appearance identifiers and a tested empty/none value only. Show incompatible selections when model constraints are proven. Preserve unknown values and the other field. |
| Skin and hair colors | Two three-component float32 vectors, skin then hair. Load invokes the corresponding setters. | Preview finite normalized RGB values in [0, 1] as a proposed initial editor limit, pending verification against the character creation palettes and color space. Preserve out-of-range legacy values until explicitly edited. Write only the selected vector. |
| Forsaken power and cooldown | Player head has power string and float32 cooldown. Load uses the power setter from player v23 and reads the cooldown from v24. | Exact build status-effect identifiers with verified empty sentinel. Finite cooldown seconds, 0 through verified power cooldown. Changing selection and keeping/resetting cooldown must be explicit. Leave world progression and boss records alone. |
| Food effects and timers | Current food block is a counted list of prefab string plus float32 remaining time. For player ≥25 the inspected loader takes remaining time and resolves prefab via ObjectDB, skipping unresolved entries. Older code branches use different representations. Effects are derived from the resolved item and time, and `UpdateFood` recalculates max health, stamina and eitr. | Verify food type, duration, duplicate rules and active-slot count per build. Require finite positive remaining time through verified burn time. Remove via explicit action. Preserve unknown records in ULF even if the game itself skips them. Leave unsupported legacy food layouts and temporary status-effect editors read-only. |
| Current health | Player head stores maximum health and current health as float32. The inspected loader substitutes its max health when current is nonpositive, greater than max or NaN. Food recalculation can later change max health. | Permit finite positive current health up to verified loaded/runtime max. Preserve both maximum and unrelated fields unless explicitly approved. Warn that the in-game value can be recalculated or changed after load. |
| Current stamina | Head stores maximum stamina. Current stamina is stored after skills and player custom data in the inspected writer. Load clamps current against the loaded maximum. Food update can recalculate maximum. | Explicit finite current in [0, verified maximum]. Keep maximum and all opaque tail data unless a separate policy permits an edit. |
| Current eitr | The current writer stores maximum eitr then current eitr after current stamina. Load sets maximum and clamps current to its range. Food updates can recalculate maximum. | Explicit finite current in [0, verified maximum]. Allow zero when no verified source grants eitr. Avoid injecting permanent max eitr. |

The v34 tail includes custom data, stamina/eitr values, build UI bytes, pseudo-counter entries and upgrade seed entries. Establish version gates by inspecting both writer and reader and building synthetic fixtures. Treat unknown and legacy tails as opaque. Runtime acceptance must compare first load and game resave because a successful binary round-trip can coexist with recalculated state.

## 5. Knowledge, progression and skill design

| Record | Evidence and dependencies | Proposed support |
|---|---|---|
| Known recipes and build pieces | `Player.Save` writes a counted string set. `AddKnownRecipe` uses the recipe item's shared name token. `AddKnownPiece` shares the set with piece name tokens. Several definitions can share a token. Recipe availability can depend on station and material knowledge and actual recipe requirements. | Show grouped tokens and dependent records, with an exact versioned token allowlist. Add only verified tokens after preview. Preserve unknown tokens. Keep build UI bytes, crafting history, item counts and world flags protected. |
| Known materials | Counted strings. `AddKnownItem` keys by item shared name, and trophy handling is separate. `UpdateKnownRecipesList` and available piece logic can recalculate availability. | Verify tokens against ObjectDB. Offer additive knowledge edits without granting inventory, trophies or recipes implicitly. Show any explicitly proposed dependent additions. |
| Known crafting stations | Counted map of station name token → int32 level. `AddKnownStation` records a higher observed level and calls `UpdateKnownRecipesList` on changes. The actual world station is independent of this record. | Bound level by verified station/build definitions. Preserve unknown stations and duplicate or unusual records. Explain that knowledge does not create or upgrade a station in the world. |
| Biomes, tutorials, texts | Current writer stores biome names as strings. The reader has version-dependent biome handling, including older integer layouts. Tutorials, uniques, trophies and known text are distinct serialized collections. Known texts use key/value strings. | Start with inspection. Add writes only after proving exact identifier, representation and gameplay role for each collection. Keep achievement-adjacent history and unknown records protected. Avoid coupling discover biome, map reveal, boss state, trophies and tutorial flags. |
| Other unlocks | Some records are player-local, some are profile or world scoped, and many derive from build/world configuration. | A feature must identify scope and dependency before enabling a write. Keep unknown collections, world keys, protected stats, build UI bytes and command history untouched. |
| Skills, XP and presets | `Skills.Save` emits v2 with ID, float32 level and float32 accumulator. ULF already edits level and XP transactionally with preserve-by-default semantics. The accumulator is not a generic XP percentage. | Versioned local data-only presets, known stable skill IDs, optional explicit XP per row, preview and confirmation. Reject or report unsupported and duplicate records without partial application. Preserve omitted fields exactly. Any percent/next-level display requires separate verified progression formula and boundary evidence. |

Build a read-only dependency graph from item, recipe and station definitions. Use it for explanations and an explicit companion-change preview. Preserve the original ordering and encoding of untouched records. Avoid cascading deletions until a game test establishes what gets rediscovered and whether the removal persists.

## 6. Offline mod support

Accept optional user-local, declarative metadata with a mod namespace and version, game-build range, canonical prefab and signed hash, source provenance and field-level verification. Preserve an ambiguous hash as unknown. Never replace a vanilla entry silently. Require an explicit selected overlay and a recorded conflict decision for any overlapping claim. Model variant, durability applicability and trusted stack maximum separately. Allow only supported, bounded formula identifiers and finite coefficients. Custom Lua/C#/Python, network lookups, runtime injection and executable expressions are outside the data contract.

For an unknown record, a verified exact hash-to-limit mapping may permit only an explicit quantity edit. The operation must preserve every other byte, including explicit default flags and noncanonical encoding. If the quantity field was absent, the only additional changes allowed are its presence bit and necessary quantity encoding. An unverifiable or ambiguous record is inspection-only and must survive Save As. Unknown records cannot be removed, cloned, relocated, normalized or reinterpreted through a bulk operation.

## 7. Architecture and verification

- **Codec by verified version.** Keep the engine Qt-independent. Introduce named spans or bounded readers for proven sections. Preserve original ordering and raw encodings and verify a byte-identical parse/serialize before enabling edits. Separate structural version dispatch from game-build statistics. Preserve profile history, player tail and cheat metadata. Avoid upgrading on save by default. Permit a future migration only with its own approved contract and fixtures.
- **Catalog and calculator.** Use a deterministic local snapshot and a pure calculation layer. Give capability checks typed reasons such as verified, missing, inapplicable and conflicting. Expose inspectable data separately from authoritative write limits. Pin a snapshot for each proposal. No game assembly or extraction dependency in runtime.
- **Transactions and review.** Validate intent against the same baseline and working revision at preview and apply. Use stable record IDs and a protected-field allowlist. Batch candidate state, verify all commands and serialize/reparse before publishing changes in memory. Keep invalid proposals and stale confirmations from partially applying. Reuse the desktop session for drafts and review, with a domain command layer for bulk or cross-section work.
- **Export verification.** Extend expected-diff checks only for fields explicitly authorized by a proposal. Keep source identity checks, immutable input, checksum, read-back and atomic Save As. Verify candidate bytes and semantics and retain edit state on failure.
- **Acceptance matrix.** Include headless synthetic fixtures for baseline and separately approved new layouts, noncanonical fields, unknown custom records, duplicate IDs/positions, build mismatches, invalid/overflow/NaN values, stale proposals, full inventory, replacement, recovery and export failures. Verify original and unrelated bytes exactly. Use Windows 10 and Linux native offline workflows, keyboard/focus and Qt responsiveness tests, and disposable in-game load, play and resave. Record app, format, game build and platform. No real character saves in Git or external services.

Principal risks are false compatibility from simply widening version guards, wrong metadata treated as authority, current game rewrites of food/equipment or history, float32 and fixed-point divergence, stale bulk confirmation, alias overwrite and overbroad redistribution. The gates above require direct evidence for each risk before the corresponding write path becomes available.
